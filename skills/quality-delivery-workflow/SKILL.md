# 高质量交付与独立审查

## 使用方式与边界
默认进入实施模式；明确指定“独立审查”时进入审查模式。项目事实与长期约束从项目规则读取，本次目标、范围和验收要求从用户任务读取，不把特定项目资料写进本 skill。
本流程不替代项目规则、环境权限或安全要求，不额外授权提交、推送、对外消息、生产操作或删除数据。不要访问无关秘密。

## 第一轮：调查与方案确认
1. 先不修改代码。读取项目规则、相关实现、测试及必要参考，优先查找已有机制，按需扩展调查。
2. 输出简短方案：目标与非目标；当前行为与代码依据；已确认事实、关键假设与不确定项；建议方案及更简单的替代方案；最小修改范围；验收案例、验证入口与主要风险。
3. 验收应覆盖适用的正常、边界、失败与回归路径。涉及并发、持久化、兼容性、性能或安全时，说明相关不变量及专项检查。参考实现和测试通过都不是正确性证明。
4. 建议合理的时间、尝试次数或资源预算。关键语义不明确时提出具体问题，不静默猜测。
5. **暂停等待用户确认方案，再开始修改。** 若用户已经明确确认当前具体方案，不必重复确认；笼统的“完成任务”不视为确认尚未提出的方案。

## 第二轮：实施与验证
1. 按已确认方案做范围明确、便于审查的修改，不顺手重构。不扩大需求，不自行改变验收语义。出现推翻方案的新证据或需要扩大范围时，先说明并等待确认。
2. 修复缺陷时，适用且可行则先建立修改前失败的测试；无法复现时说明证据缺口，不把新增测试通过等同于已修复。新功能覆盖已约定的验收场景。
3. 执行实际构建、测试和适用的专项检查，记录命令、必要环境、代码版本及真实结果。不能运行时标明未执行和原因，不把建议检查或推断写成通过。
4. 根据失败证据修正实现，不为通过检查而删除测试、削弱断言、跳过失败路径或改变预期行为。性能结论需有基线、重复测量和噪声说明。
5. 超预算、持续无进展、依赖阻塞或需关键人类决策时停止，交接当前版本、变更、事实、假设、命令结果、阻塞与下一步。不绕过权限限制。

## 第三轮：证据交付与审查交接
交付完成情况、修改摘要、实际验证及未执行项、剩余风险。最终接受与合入由用户决定。
同时给出可复制到新会话的简短交接：

```text
使用 Quality Delivery Workflow 的独立审查模式。
原始需求：［必要原文］
项目约束与不变量：［内容及来源］
变更范围：［基准与目标版本、文件范围；未提交改动注明状态］
验收标准：［可核查条件］
验证入口与环境：［命令及前提］
请独立检查当前代码差异，寻找可验证的问题，暂不修改代码。
```

交接应保持中性，不夹带实现者的辩护结论或暗示性评价。用户另开干净会话，或使用环境明确支持的独立 agent。**同一会话切换角色不算独立审查。** skill 不自动创建会话，也不假定任何 CLI 支持特定调度功能。尚未独立执行时，明确标记独立审查未完成。

## 独立审查模式
1. 从原始需求、项目约束和实际差异出发，先独立检查，再按需参考实现者解释。
2. 检查需求遗漏、错误假设、边界行为、兼容性、无关修改，以及测试是否仅重复实现逻辑。默认不改代码、不自行修复。
3. 环境和用户授权允许时运行验证；构建与测试可在隔离目录生成必要产物，但不因此修改源代码、测试或断言。避免生产、外部服务和破坏性副作用；需要额外权限时按环境规则申请。
4. 仅报告有依据的问题：位置、触发条件、违反的需求或不变量、影响及可核查证据。疑点单列并说明证据缺口，不凑数；未发现问题不等于无缺陷。
5. 将核实的问题交给用户确认修复范围，再由实施会话修复；修复后重跑相关验证并更新证据。

## 调用示例
- 新需求：“使用 Quality Delivery Workflow 处理以下需求：［目标、范围、约束、验收条件］。先调查并提出方案。”
- 新会话：“使用 Quality Delivery Workflow 的独立审查模式，以下是需求与交接：［内容］。”
